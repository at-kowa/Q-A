| 項目 | 内容 |

## 1. 検証の目的

- supabase・GitHub・Vercel を組み合わせた構成で、**開発者本人が Claude Code を使ってアプリを開発し、公開まで行えるか**を確かめる
- 確かめるのは「アプリが作れるかどうか」であり、業務での効果（工数削減など）は検証しない
- 質問箱アプリは、ログイン・権限・データ保存・画像保存・公開などの技術要素を一通り含む**題材**として選んでいる

### 1.1 題材アプリの概要

- 利用者が質問・要望・不具合を投稿し、情シスが担当を決めて回答する
- 汎用的な回答は、情シスが編集して社内FAQとして公開する

## 2. 今回の位置づけと範囲

### 2.1 位置づけ

- **技術検証版**とする。業務での本番運用は行わない
- 投稿は**テスト投稿のみ**とし、実際の問い合わせは受け付けない
- 検証の範囲は**開発＋公開まで**とする（公開後の保守・運用は検証しない）

### 2.2 対象

- 7章の「必須」機能の画面、ログイン、データ保存（supabase）、添付画像の保存、Vercel への公開
- 最初から supabase の実際のデータベースで作る（モック実装は作らない）

### 2.3 対象外

- 業務での本番運用、実際の問い合わせの受け付け
- 会社の有償 Vercel チーム・本番用 supabase での構築
- メール・Teams 等への自動通知
- kintone 等とのデータ連携
- 7章で「今回はやらない」とした機能

## 3. 検証計画

### 3.1 進め方

| 項目 | 内容 |
|---|---|
| 確認する人 | 開発者本人（必要に応じて情シスのメンバーが協力） |
| アカウント | 「一般」「情シス担当」「管理者」のテスト用アカウントを使い分けて動作を確認する |
| データ | テスト投稿・テスト用FAQのみ（架空の内容） |
| 期間 | 定めない |
| 成功の判定 | 17章の受け入れ基準をすべて満たしたら「この構成で作れる」と判定する |
| 検証後のデータ | テストデータ・添付画像・アカウントはそのまま残す |
| 記録 | 検証の記録は残さない（アプリと README のみ） |

### 3.2 確かめる技術要素

| 技術要素 | 使うもの | 確かめること | 受け入れ基準（17章） |
|---|---|---|---|
| ログイン | supabase Auth | 社員番号＋パスワードでログインでき、初回のパスワード変更を強制できる | 機能 1 |
| 権限ごとのアクセス制御 | supabase RLS・DB関数 | 一般／情シス担当／管理者で、読み書きできるデータを DB 側で分けられる | 安全性 1〜3 |
| データの保存と一連の流れ | supabase Database | 投稿→割り当て→回答→FAQ公開を DB に保存しながら最後まで動かせる | 機能 2 |
| 画像の保存 | supabase Storage | 非公開バケットに画像を保存し、権限のある人だけが表示できる | 機能 1・安全性 1 |
| 新着の自動表示 | 一定間隔の取得 | 開いている画面に新しい投稿が自動で表示される | 機能 3 |
| ソース管理と変更の流れ | GitHub | ブランチ→PR→本人のマージ、の流れで開発を進められる | 運用 1 |
| DB の変更 | SQL ファイル＋SQL Editor | migration の SQL を Claude が作り、本人が適用する流れで DB を作れる | 運用 2 |
| 公開 | Vercel | 接続キーを commit せずに、環境変数から設定して公開できる | 公開 1〜2 |
| 社内環境の制約 | － | npm・supabase CLI が使えない PC でも開発・公開できる | 公開 1 |

### 3.3 検証しないこと

- 業務での効果（工数削減・使いやすさの評価など）
- 公開後の保守・運用（不具合修正の反映、利用者の追加・削除の運用など）
- 実際の利用者による利用

## 4. システム構成

### 4.1 全体構成

```
[利用者：Edge（Windows PC／iPad）]
        │  HTTPS
        ▼
[Vercel（Hobby）] … 画面ファイル（HTML／CSS／JS）を配信するだけ。データは置かない
        │
        │  supabase-js（ブラウザから直接）
        ▼
[supabase（チーム共有プロジェクトに間借り）]
   ├─ Auth      … ログイン（社員番号＋パスワード）
   ├─ Database  … qbox_ で始まるテーブル。RLS でアクセスを制御
   └─ Storage   … 添付画像（非公開バケット）

[GitHub（at-kowa/Q-A）] … ソースコードの管理。main にマージされると Vercel が自動で公開
```

### 4.2 使用サービスと役割

| サービス | 役割 | 利用形態 |
|---|---|---|
| GitHub | ソースコード管理、変更の確認（プルリクエスト） | 会社の Organization（at-kowa）のリポジトリ `Q-A` |
| supabase | ログイン、データベース、添付画像の保存 | チームのテスト用プロジェクトに間借り。作るものはすべて `qbox_`（Storage は `qbox-`）で始める |
| Vercel | 画面ファイルの公開 | 会社メールで登録した無償プラン（Hobby）。試作・検証目的に限る |

### 4.3 環境

| 環境 | 用途 | URL・場所 |
|---|---|---|
| ローカル | 開発中の動作確認 | PC 上で HTML を開く（簡易サーバで起動） |
| プレビュー | プルリクエストごとの確認 | Vercel が PR ごとに自動で作る URL |
| 検証公開 | 公開できたことの確認に使う画面 | Vercel の本番 URL（main ブランチ） |

- データベースは3つの環境で同じ supabase（共有プロジェクト）を使う
- 検証に協力する人以外には URL を案内しない

### 4.4 フロントエンドの作り

- **ビルド不要の静的ファイル**（HTML／CSS／JavaScript）で作る。この PC は npm が使えないため、npm に頼らない
- supabase との通信は supabase-js を使う。CDN から**バージョンを固定して**読み込む
- 接続先（supabase の URL と公開用キー）は `config.js` に書き、**GitHub には commit しない**。Vercel では環境変数から `config.js` を生成する（qbox-test の仕組みを流用）
- 画面（View）、状態管理、データアクセス（Repository）の3層に分け、supabase を呼ぶ処理は Repository にまとめる
- 処理はすべて非同期（async/await）で書く

### 4.5 フォルダ構成（案）

```
Q-A/
├─ app/
│   ├─ index.html          … 画面（シングルページ）
│   ├─ css/
│   ├─ js/
│   │   ├─ views/          … 画面ごとの処理
│   │   ├─ repositories/   … supabase を呼ぶ処理
│   │   └─ main.js
│   └─ config.js           … 接続先（commit しない）
├─ supabase/
│   ├─ migrations/         … DB 変更の SQL（日付順のファイル）
│   └─ seed/               … テストデータ・マスタの SQL
├─ scripts/write-config.mjs … Vercel で config.js を作る
├─ vercel.json
├─ CLAUDE.md               … このアプリ固有のルール
└─ README.md               … 構成・起動方法・保守手順
```

## 5. 社内ルール・制約

- 動作対象ブラウザは **Microsoft Edge**（Windows PC・iPad）。iPad は縦・横どちらでも使えること
- 通信先は **supabase と Vercel のみ**。アクセス解析タグ、自動メール・Webhook 送信、その他の外部 API は使わない（CDN は supabase-js の読み込みのみ）
- **アクセス制限なしで公開しない**。ログインしないとデータを一切読めない設計にする
- Vercel Hobby は試作・検証用。業務の本番運用はしない
- 共有プロジェクトでは、`qbox_` 以外のテーブルやプロジェクト全体の設定（Auth の設定を含む）に触れない
- テスト投稿・添付にも**個人情報（パスワード・口座番号・マイナンバー等）、図面、取引先・顧客から預かった資料**を入れない。画面に注意書きを出す
- 接続キー・パスワードはコードやチャットに書かない。`service_role`（secret）キーは使わない
- 情報システム部で維持・保守する前提とし、README に保守手順を書く

## 6. 利用者と権限

| 権限 | 想定ペルソナ（題材としての設定） | できること |
|---|---|---|
| 一般 | 現場リーダー、工場事務 | 投稿、自分の投稿の閲覧・コメント・取り下げ、公開FAQの閲覧・検索、「同じ困りごと」登録 |
| 情シス担当 | 情シス（ベテラン・若手） | 一般の操作すべて＋全投稿の閲覧、担当割り当て、ステータス変更、回答、コメント、公開設定 |
| 管理者 | 情シス責任者 | 情シス担当の操作すべて＋FAQの削除 |

- 検証では、それぞれの権限のテスト用アカウントを作って動作を確認する
- 権限は画面の表示切り替えだけでなく、**データベース側（RLS）でも必ず制御**する

## 7. 機能の優先度

| 区分 | 機能 |
|---|---|
| **必須**（今回作る） | ログイン・パスワード変更、ホーム（簡易）、新規投稿（添付画像を含む）、投稿完了、自分の投稿一覧、投稿詳細（投稿者用・対応用）、受付一覧、**受付一覧・ホームの自動更新**、担当割り当て、ステータス変更、コメント・内部メモ、回答、FAQ公開編集、FAQ一覧・検索・詳細、未読バッジ |
| **あれば良い**（必須が終わってから） | 件名入力中のFAQ候補表示、入力中の一時保存、変更履歴の表示、「解決した／同じ困りごと」ボタン、対応期限、新しいFAQ5件の表示 |
| **今回はやらない** | 集計画面（S-13）、CSV出力、マスタ管理画面（S-14）、複数投稿の一括割り当て、回答ひな形、類似投稿の候補表示、利用者の一括登録 |

- 「今回はやらない」の機能で必要なデータ（拠点・場所・カテゴリ・利用者）は、SQL で直接登録する（`supabase/seed/`）

## 8. 認証（ログイン）

### 8.1 方式

- **社員番号＋パスワード**でログインする
- supabase Auth のメール＋パスワード方式を使い、社員番号を内部用のメール形式（`<社員番号>@qbox.example.com`）に変換してログインする。利用者には社員番号だけを入力してもらう
- この内部用アドレスにはメールが届かないため、メールによる確認・パスワード再設定は使わない

### 8.2 利用者の登録と識別

- Auth のアカウントは、開発者本人が supabase の管理画面で手入力で作成する（「メール確認済み」として作成）
- 初期パスワードは本人が対面で伝え、初回ログイン時に変更してもらう
- アプリ側の利用者情報（氏名・部署・拠点・権限・有効／無効）は `qbox_users` で管理し、SQL で登録する
- **`qbox_users` に登録され、かつ有効な人だけ**がアプリのデータを読み書きできる。共有プロジェクトの他アプリの利用者がログインしても何も見えないようにする

### 8.3 その他

- 未ログインの場合はすべての画面をログイン画面へ誘導する（公開FAQも含む）
- 一定時間操作がない場合は自動でログアウトする（初期値60分、設定値）
- 初回ログイン時と、パスワード初期化後はパスワード変更を必須とする（`qbox_users` の「変更が必要」フラグで判定）
- パスワードの保管は supabase Auth に任せ、アプリでは保持・表示しない
- パスワード初期化の具体的な方法（管理画面での操作）は実装時に確認し、README に手順を書く

## 10. 画面ごとの要件

「あれば良い」の項目には【あれば良い】と記す。

### S-03 ホーム

- 画面上部に大きな「質問・要望を送る」ボタンを置く（iPadで押しやすい大きさ）
- FAQの検索窓を置く。**投稿の前に先に検索してもらう導線**にする
- 「自分の投稿」の件数と、未読の回答・コメントのバッジを表示する
- 情シス担当には「未対応」「自分の担当」の件数を表示する。開いている間は自動更新する（12章）
- 【あれば良い】新しく公開されたFAQを5件表示する

### S-04 新規投稿

入力項目：

| 項目 | 必須 | 形式 | 備考 |
|---|---|---|---|
| 種別 | ○ | 選択（質問／要望／不具合） | アイコン付きの大きなボタンで選ぶ |
| カテゴリ | ○ | 選択 | PC・周辺機器／業務システム／アカウント・権限／ルール・使い方・AI利用／その他 |
| 工場・拠点 | ○ | 選択 | 初期値はログインした利用者の所属拠点 |
| 場所 | － | 選択＋自由入力 | 拠点に応じて選択肢を切り替える |
| 件名 | ○ | テキスト（40文字以内） | |
| 内容 | ○ | 複数行テキスト（2,000文字以内） | 種別ごとに書き方の例を表示する |
| 発生日時 | 種別が不具合のときは必須 | 日時 | 初期値は現在日時 |
| 緊急度 | ○ | 選択（業務が止まっている／困っているが回避できる／急がない） | 初期値は「急がない」 |
| 添付ファイル | － | 画像（jpg／png） | 最大3枚。iPadのカメラで撮影できるようにする。サムネイルをプレビューする。保存前にブラウザで縮小する（長辺1,600px・JPEG、1枚おおむね1MB以下） |
| 公開の可否 | － | チェックボックス | 「FAQとして公開されても構わない」。最終的な公開は情シスが判断する |

- 投稿者の氏名・部署・社員番号はログイン情報から自動で設定する（入力させない）
- 送信前に確認画面を表示する
- 注意書きを表示する：「パスワード・口座番号・マイナンバーなどの個人情報や、図面・お客様からお預かりした資料は書かない・添付しないでください」
- 【あれば良い】件名を入力している途中で、似ている公開FAQを候補として表示する
- 【あれば良い】入力中の内容をブラウザ内に一時保存する（送信後に消す）

### S-05 投稿完了

- 受付番号（例：`Q-2026-00123`）、件名、「自分の投稿一覧」へのリンクを表示する
- 受付番号はデータベース側で採番する（重複しないこと）

### S-06 自分の投稿一覧

- 列：受付番号、件名、種別、ステータス、最終更新日時、未読マーク
- ステータスで絞り込みできる（初期表示は「完了」以外）
- iPadではカード形式で表示する

### S-07 投稿詳細（投稿者用）

- 投稿内容、添付画像、ステータス、担当者名、回答、コメントのやり取りを時系列で表示する
- コメントを追加できる（情シスからの追加質問への返信）。画像添付も可能にする
- 「受付」状態のあいだだけ、投稿を取り下げられる
- 開いた時点で未読を既読にする
- 情シス内部メモは表示しない（データベース側でも読めないようにする）

### S-08 公開FAQ一覧・検索

- キーワード検索（タイトル・質問文・回答文が対象）
- カテゴリ・種別で絞り込みできる
- 並べ替え：新しい順
- 投稿者名は表示しない

### S-09 FAQ詳細

- 公開用のタイトル・質問・回答・公開日・カテゴリを表示する
- 解決しない場合は「この内容で質問する」ボタンを置き、カテゴリを引き継いでS-04を開く
- 【あれば良い】「解決した」「同じ困りごとがある」ボタン（1人1回まで。データベースの一意制約で保証する）

### S-10 受付一覧（管理）

- 列：受付番号、件名、種別、カテゴリ、拠点、緊急度、ステータス、担当者、投稿日時、経過日数、未読マーク
- 絞り込み：ステータス、担当者（「自分」「未割り当て」を含む）、種別、カテゴリ、緊急度、キーワード
- 並べ替え：初期表示は緊急度が高い順、次に投稿日時が古い順
- 「業務が止まっている」の投稿は行を色分けし、アイコンも付けて目立たせる
- **自動更新**：開いている間は一定間隔で新着を取得し、新しい投稿を目立たせる（12章）

### S-11 投稿詳細（対応用）

- 投稿内容と添付画像を表示する。画像は拡大表示できる
- 操作：
  - 担当者の割り当て・変更
  - ステータスの変更（11章のとおり）
  - 投稿者へのコメント（追加質問）
  - **情シス内部メモ**（投稿者には表示しない）
  - 回答の登録（回答を登録するとステータスを「完了」にするか確認する）
  - 公開設定：非公開（初期値）／公開。公開を選ぶとS-12へ進む
- 【あれば良い】対応期限の設定
- 【あれば良い】変更履歴（誰が・いつ・何を変更したか）の表示

### S-12 FAQ公開編集

- 元の投稿をもとに、公開用のタイトル・質問文・回答文を編集できる（個人名・固有の情報を取り除くため）
- 公開前にプレビューを表示する
- 公開したFAQは非公開に戻したり、編集したりできる
- 投稿者が公開の可否にチェックしていない場合は警告を表示する（公開すること自体はできる）
- 元の投稿の添付画像はFAQに引き継がない

## 11. ステータス

| ステータス | 意味 | 変更できる人 |
|---|---|---|
| 受付 | 投稿された直後。担当者がまだ決まっていない | 自動 |
| 対応中 | 担当者が決まり、対応している（追加質問中も含む） | 情シス担当 |
| 完了 | 回答済み・対応済み・見送り・取り下げ | 情シス担当（取り下げは投稿者） |

- 担当者を割り当てると、自動で「対応中」にする
- 「完了」にするときは**完了区分**（回答済み／対応済み／見送り／取り下げ）を必須で選ぶ
- 完了した投稿に投稿者がコメントした場合は、「対応中」に戻すかどうかを情シスが判断する（未読バッジで知らせる）
- ステータスの変更ルールはデータベース側でもチェックする（一般の利用者が自分で「完了」にできない等）

## 12. 通知と自動更新

- メール・チャットへの自動送信は行わない（社内ルール）
- **未読バッジ**
  - 投稿者：回答の登録、コメントの追加、ステータスの変更があったときに未読にする
  - 情シス担当：新しい投稿、自分が担当する投稿へのコメントがあったときに未読にする
  - ヘッダーに未読件数を表示し、クリックすると未読の一覧を表示する
- **自動更新**（新しい投稿に気づくための仕組み）
  - 受付一覧（S-10）とホーム（S-03）を開いている間、一定間隔（初期値60秒、設定値）で新着と未読件数を取得する
  - 新着があれば一覧の上部に表示して目立たせ、ブラウザのタブのタイトルにも件数を出す（例：`(2) 受付一覧`）
  - 共有プロジェクトの設定を変えずに済むよう、一定間隔での取得で実現する（リアルタイム配信の機能は使わない）

## 13. データ設計

### 13.1 テーブル（supabase）

すべて `qbox_` で始める。主キーは原則 `id`（自動採番または uuid）。

| テーブル | 内容 | 主な項目 |
|---|---|---|
| qbox_users | 利用者 | Auth のユーザーID、社員番号、氏名、部署、所属拠点ID、権限、有効フラグ、パスワード変更が必要か、最終ログイン日時 |
| qbox_sites | 拠点 | 名称、表示順、有効フラグ |
| qbox_locations | 場所 | 拠点ID、名称、表示順、有効フラグ |
| qbox_categories | カテゴリ | 名称、表示順、有効フラグ |
| qbox_tickets | 投稿 | 受付番号、種別、カテゴリID、拠点ID、場所ID、場所（自由入力）、件名、内容、発生日時、緊急度、公開可否（投稿者の希望）、投稿者ID、担当者ID、ステータス、完了区分、対応期限、投稿日時、更新日時、完了日時 |
| qbox_comments | コメント | 投稿ID、書いた人のID、本文、内部メモかどうか、日時 |
| qbox_answers | 回答 | 投稿ID、回答本文、回答者ID、日時 |
| qbox_attachments | 添付画像の情報 | 投稿ID またはコメントID、Storage 上のパス、ファイル名、種類、サイズ、登録者ID |
| qbox_faqs | FAQ | 元の投稿ID、公開タイトル、公開質問文、公開回答文、カテゴリID、公開状態、公開日時、更新日時 |
| qbox_reactions | FAQへの反応【あれば良い】 | FAQ ID、利用者ID、種類（解決した／同じ困りごと）。3項目で一意 |
| qbox_read_states | 既読 | 利用者ID、投稿ID、最後に読んだ日時 |
| qbox_histories | 変更履歴【あれば良い】 | 投稿ID、変更者ID、変更項目、変更前、変更後、日時 |
| qbox_settings | 設定値 | キー、値（自動ログアウト時間、自動更新の間隔など） |

- 回答ひな形（qbox_templates）は今回は作らない

### 13.2 添付画像（Storage）

- 非公開のバケット `qbox-attachments` に保存する
- 表示するときは、権限を確認したうえで期限付きのURLを発行して表示する
- 検証後もそのまま残す。共有プロジェクトの容量に注意する

### 13.3 アクセス制御（RLS）の方針

- すべてのテーブルと Storage に RLS を設定する。**未ログイン（anon）には何も許可しない**
- 権限の判定は、ログイン中の利用者を `qbox_users` で引いて行う（判定用のDB関数を用意する）

| データ | 一般 | 情シス担当 | 管理者 |
|---|---|---|---|
| 投稿 | 自分の投稿のみ閲覧・登録。取り下げは「受付」のときのみ | すべて閲覧・更新 | すべて |
| コメント | 自分の投稿の、内部メモ以外のみ閲覧・登録 | すべて | すべて |
| 回答 | 自分の投稿のもののみ閲覧 | すべて | すべて |
| 添付画像 | 自分の投稿・コメントのもののみ | すべて | すべて |
| FAQ | 公開中のもののみ閲覧 | すべて閲覧・登録・更新 | すべて（削除を含む） |
| マスタ | 閲覧のみ（有効なもの） | 閲覧のみ | 閲覧のみ（登録は SQL で行う） |
| 利用者 | 自分の情報の閲覧のみ | 閲覧（担当者選択のため） | 閲覧（登録は SQL で行う） |
| 変更履歴 | 閲覧不可 | 閲覧 | 閲覧 |

- 自分の権限・有効フラグは本人が変更できないようにする
- 「パスワード変更が必要」フラグの解除は、専用のDB関数を通してのみ行う

### 13.4 データベース側の処理

- 受付番号の採番（`Q-年-5桁連番`）
- 更新日時の自動更新
- 担当者を割り当てたときに「対応中」にする
- 【あれば良い】投稿の変更履歴の自動記録（担当者・ステータス・期限・公開設定）

## 14. セキュリティ

- 画面に表示する際は入力値をエスケープする（XSS対策）
- 権限のない画面へURLを直接入力しても表示しない。ただし本当の防御はRLSで行う（画面の制御だけに頼らない）
- フロントエンドでは公開用（anon／publishable）キーだけを使う
- 接続キー・`.env`・`config.js` は commit しない。Vercel の環境変数は本人が管理画面で登録する
- リポジトリは Public のため、社内の情報（拠点名・利用者名などの実データ、社内URL）をコードやテストデータに書かない。マスタの実データは supabase 上にだけ登録する

## 15. 非機能要件

- 操作性：iPadのタッチ操作を前提に、ボタンなど押す部分は44px以上にする。2〜3分で投稿を終えられること
- 文言：専門用語を避け、平易な日本語にする
- 表示速度：一覧の表示は1秒以内（500件程度のデータで）。一覧はページ分割して取得する
- アクセシビリティ：文字とボタンのコントラストを確保し、色だけで情報を伝えない
- 個人情報：投稿画面に注意書きを表示する。公開FAQには投稿者の情報を表示しない
- 可用性：検証版のため、停止・データ消失のおそれがある。共有プロジェクトのプランによっては一定期間使わないと停止する場合がある

## 16. 開発の進め方

### 16.1 役割分担

| 作業 | 担当 |
|---|---|
| 作業ブランチ作成・実装・テスト・commit・push・プルリクエスト作成 | Claude（本人の許可後） |
| プルリクエストの確認と main へのマージ | 本人 |
| DB 変更・テストデータ・マスタ登録の SQL 作成（`supabase/` にファイルとして作る） | Claude |
| SQL の適用（supabase の SQL Editor に貼り付けて実行） | 本人 |
| Auth の利用者作成・パスワード初期化、Storage バケット作成 | 本人 |
| Vercel の環境変数登録・プロジェクト設定 | 本人 |

### 16.2 Git の運用

- main で直接作業しない。1つの作業ごとに `feat/…` `fix/…` `chore/…` のブランチを切る
- 1つのプルリクエストは1つの段階（16.4）にする
- commit メッセージとプルリクエストの説明は日本語で書き、プルリクエストには変更内容と確認方法を書く

### 16.3 DB の変更と公開

- テーブル追加・変更、RLS、DB関数はすべて `supabase/migrations/` の SQL ファイルとして作り、プルリクエストに含める
- 本人が SQL Editor で実行し、実行したことをプルリクエストにコメントする
- プルリクエストを作ると Vercel がプレビューURLを作るので、そこで確認する。main にマージすると検証公開URLに反映される

### 16.4 開発の段階（プルリクエストの単位）

| 段階 | 内容 | 優先度 |
|---|---|---|
| 1 | 土台：フォルダ構成、ログイン・ログアウト・パスワード変更、`qbox_users`・マスタのテーブルとRLS、マスタ・テストデータのSQL | 必須 |
| 2 | 投稿：新規投稿（添付画像を含む）、投稿完了、自分の投稿一覧、投稿詳細（投稿者用） | 必須 |
| 3 | 対応：受付一覧（自動更新を含む）、投稿詳細（対応用）、ステータス、コメント・内部メモ、回答、未読バッジ、ホーム | 必須 |
| 4 | FAQ：FAQ公開編集、FAQ一覧・検索・詳細、README | 必須 |
| 5 | 追加：7章の「あれば良い」から本人と相談して選ぶ | あれば良い |

- 開発の着手は本人の許可（「いいよ」）を得てから。許可後は段階1〜4を順に進める

## 17. 受け入れ基準（検証の成功判定）

次をすべて満たしたら「この構成で Claude Code を使ってアプリを作れる」と判定する。

| 区分 | No | 基準 |
|---|---|---|
| 機能 | 1 | 3つの権限それぞれのテスト利用者でログインし、「必須」のすべての画面を表示・操作できる（画像の添付・表示を含む） |
| 機能 | 2 | 投稿→担当の割り当て→コメントのやり取り→回答→完了→FAQ公開の一連の流れを最後まで実行できる |
| 機能 | 3 | 受付一覧を開いたまま別の利用者が投稿すると、設定した間隔のうちに新着として表示される |
| 機能 | 4 | 未読バッジが12章のとおりに増減する |
| 機能 | 5 | Edge（PC）と、iPad（縦・横）で画面が崩れない |
| 安全性 | 1 | ログインしていない状態で、どのテーブル・画像も取得できない |
| 安全性 | 2 | 一般の利用者が他人の投稿・内部メモ・変更履歴を取得できない |
| 安全性 | 3 | `qbox_users` に登録されていない（または無効の）アカウントでは何も取得できない |
| 運用 | 1 | すべての変更が作業ブランチ→プルリクエスト→本人のマージで main に入っている |
| 運用 | 2 | DB の構成がすべて `supabase/migrations/` の SQL ファイルとして残っている |
| 公開 | 1 | Vercel の検証公開URLで、上の機能がすべて動く |
| 公開 | 2 | GitHub に `config.js`・接続キーが含まれていない |
| 公開 | 3 | 通信先が supabase・Vercel・supabase-js の CDN のみである（開発者ツールのネットワークタブで確認する） |

## 18. 本番化する場合に必要なこと（今回は対象外）

- 業務上の目的と効果の整理、実際の利用者を入れた評価
- 公開後の保守・運用の流れ（不具合修正の反映、利用者の追加・削除など）
- 基盤の比較と選択：会社の有償 Vercel チーム＋本番用 supabase、または kintone・Microsoft Forms 等の社内標準の仕組み
- 本番用 supabase プロジェクトを分け、Auth の設定（新規登録の停止など）を行う
- 想定利用者数（100〜500名、投稿は月100件程度）に合わせた容量・プランの見直し
- 「今回はやらない」とした機能（集計・CSV・マスタ管理画面・一括登録など）の要否
- データ・添付画像の保存期間とバックアップ
- リポジトリの公開範囲（Private 化）
